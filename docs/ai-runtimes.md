# AI runtimes

Berry distinguishes four facts that are often collapsed into one label:

1. **Execution host** — the AgentCore Runtime or HTTP runtime image that receives a Berry task envelope.
2. **AI runtime** — the model client or provider-owned agent process inside that host.
3. **Model provider** — the service that serves the selected model.
4. **Authentication and billing** — the account, credential, entitlement, and quota charged for the call.

Installing an agent framework does not grant model access. A consumer subscription is used only where the provider documents that path. Berry never extracts browser cookies, reads another CLI's credential store, impersonates a first-party client, or falls back to API billing or another account.

The desktop VS Code companion can run Kiro, Claude Code and Codex on the
person's machine while hosted Berry remains the control plane. Use **Berry:
Start workstation CLI bridge** in a trusted local folder after signing in with
the official CLI. It pulls one run at a time over outbound `/api/v1`, matches
the project's GitHub remote (or requires a single open folder), and posts
lifecycle events to Berry's ledger with leased ownership and cancellation.
It copies no login stores, creates no second checkout, and never falls back
to API billing. See [companion setup](../apps/vscode/README.md).

## What works in this release

**Kiro, Claude Code, Codex, Cursor, Kimi, Grok, and Qoder are the connectable subscription runtimes.** Kiro uses the Kiro CLI already signed in on this workstation: Berry starts `kiro-cli acp --agent-engine=v3 --auth-method cli` and does not read or store its credential files. An API key is not collected. Claude uses the Claude Code CLI already signed in on this workstation: Berry starts `claude` and does not read or store its credential files. An API-key login is refused, so a connection cannot switch the account onto Console billing. Codex uses the Codex CLI already signed in with ChatGPT on this workstation: Berry starts `codex exec` and does not read or store its credential files. An API-key login is refused. Cursor uses the Cursor Agent CLI already signed in with a Cursor account on this workstation: Berry starts `cursor-agent --print --output-format stream-json` and does not read or store its credential files. `CURSOR_API_KEY` and `CURSOR_AUTH_TOKEN` are stripped from the child environment, so a connection cannot switch the account onto API billing. Kimi uses the Kimi Code CLI already signed in on this workstation: Berry starts `kimi acp` and does not read or store its credential files. The CLI owns its own `kimi` / `/login` account login, so Berry forwards no API key and answers no auth-token callback; a Moonshot platform API key is a separate path and is not used. Grok uses the Grok Build CLI already signed in on this workstation: Berry starts `grok` headlessly with the prompt in a file and does not read or store its credential files (`~/.grok/auth.json`). Berry writes its MCP server into a private per-run `GROK_HOME` under the run’s state directory, never into the checkout, and links the user’s own login files in. An `XAI_API_KEY` login is refused, so a connection cannot switch the account onto API billing. Kiro runs on the user workstation, as a process Berry starts beside the server. v3 rejects `--agent`. It does not run inside the runtime container, and Kiro does not give Berry a container to start for a model. `kiro-cli chat --cloud` asks Kiro to host that whole session in its own sandbox; Berry does not set that execution target. The process uses the workstation home so the CLI login is the one that runs. Native shell and file tools are denied. Berry tools are exposed as the `berry` MCP server. The workstation process streams text, tool events, execution status, and cancellation into Berry’s existing run ledger. Model discovery for Kiro runs in that workstation process. The product server still does not call a model. GitHub sign-in and the GitHub App stay for identity and repository access. GitHub Copilot is not a Berry runtime. Qoder uses the Qoder CLI already signed in on this workstation: Berry starts `qoder --acp`, drives it over the Agent Client Protocol, and does not read its credential store or pass a Qoder PAT or API key. The first-run browser sign-in keeps the account token in the CLI's own store, so the login never enters Berry.

When Kiro is connected, Settings → Model tiers places Kiro's models on BerryMax, BerryXHigh, BerryHigh, BerryMid and BerryLow. The same model may be on more than one tier, at most three per tier, and only once inside a tier. A task or project can pin a model. Otherwise the run uses the first model on the Berry agent's tier that Kiro offers. Token counts come from Kiro's context breakdown and are stored unpriced; a credit total is not a dollar cost.

Every other requested runtime remains visible in Settings → AI Runtimes with a specific blocker. A documented local CLI is not marked available when the Berry deployment cannot safely reach that CLI's runtime-owned login.

## User setup: Kiro

Prerequisites:

- The workstation that runs Berry has the official `kiro-cli` binary on `PATH`. Berry does not ship that binary and does not start it inside the runtime container.
- The person has signed in with `kiro login` on that workstation.

Steps:

1. Open **Settings → AI runtimes**.
2. On **Kiro**, **Claude**, **Codex**, **Cursor**, or **Kimi**, select **Connect**. Berry wires that CLI on this computer (`localhost`), verifies the login, and lists models. Connect does not collect a key.
3. Connecting is enough. Agent runs in this workspace use Kiro instead of Bedrock or Kilo. Place models on the tiers under Settings → Model tiers, or pin one on the task or project. When nothing is placed and the task names no model, the run keeps the CLI's own default.
4. Start work. The run record stores `aiRuntimeId` and `aiModelId`. Usage stays on that Kiro subscription.
5. Disconnecting clears the connection and cancels active runs that used it. The CLI login stays on the workstation.

## Failure behavior

| Condition | Berry behavior | Action |
| --- | --- | --- |
| `kiro-cli` missing | `RUNTIME_NOT_INSTALLED`; no fallback | Install `kiro-cli` on the workstation PATH. |
| Kiro CLI is not signed in | `AI_RUNTIME_AUTH_REQUIRED`; no fallback | Run `kiro login` on the workstation, then connect again. |
| Model not entitled or removed | `MODEL_UNAVAILABLE`; no replacement model | Select another model returned by live discovery. |
| Subscription quota exhausted | `QUOTA_EXHAUSTED`; no API-key switch | Wait for the Kiro quota to reset, then retry. |
| Runtime network failure | `NETWORK_ERROR`, retryable | Restore egress from the runtime host and retry. |
| Person cancels login/run | No connection is recorded, or the run becomes cancelled | Start the flow again only when wanted. |
| Connection is removed mid-run | Berry cancels every active run carrying that connection id | Reconnect and explicitly restart if the work should continue. |

## Manual validation with a real account

Automated tests never call Kiro or a model. For a release candidate, use a non-production workspace and account:

1. Install `kiro-cli` on the workstation and migrate a disposable Berry database through migration 227.
2. Connect Kiro after `kiro login`. Verify Settings shows the account and a live model list.
3. Place models into BerryMax, BerryXHigh, BerryHigh, BerryMid, and BerryLow. Start a repository task and verify text, tool events, usage, and the final result appear in order.
4. Cancel while a command is running. Verify the run becomes cancelled and the `kiro-cli` child exits.
5. Start the same task as another member and verify Berry uses that member's own connection, or the workspace connection when the product allows it.
6. Select a model the account cannot use and verify Berry reports `MODEL_UNAVAILABLE` without invoking Berry-managed Bedrock/Kilo.
7. Disconnect during a run. Verify cancellation and that the sealed key is gone.
8. Inspect product-server logs. Verify no API key, task token, repository credential, or provider body appears.

## Adding a future adapter

1. **Verify the product first.** Add official links and evidence to `server-ts/src/runtime/ai-runtime-catalog.ts`. Record product identity, platforms, subscription eligibility, billing owner, auth method, machine interface, local/remote boundary, models, streaming, tools, sessions, cancellation, usage, and restrictions. Leave `availability: "blocked"` until the full path works.
2. **Choose the correct interface.** Implement `DirectInferenceAdapter` only for a model interface driven by Berry's loop. Implement `AgentProcessAdapter` when the provider owns planning, tools, permissions, sessions, or execution semantics.
3. **Keep SDK imports in the runtime image.** Provider/agent SDK imports belong under `server-ts/src/agents/runtime/` and must pass `pnpm check:models`. Pin the dependency exactly and confirm an MIT, Apache-2.0, or Elastic License 2.0 license and runtime artifact license. Elastic License 2.0 code may not be offered as a managed service, may not have its notices or license-key checks stripped, and is not relicensed to AGPL.
4. **Define credential ownership.** Prefer the runtime's official login when one persistent principal owns that host. Berry may seal a token only when the provider explicitly supports third-party/server delegation. Never read another CLI's files, browser cookies, keychain, or undocumented endpoint.
5. **Enforce the user boundary.** Resolve the connection by `(workspace_id, user_id, runtime_key)`, snapshot its id onto the run, include the connection in the runtime session key, and refuse unattended work unless the provider documents a suitable service entitlement.
6. **Normalize, do not flatten.** Map text, thought summaries, tool start/output/completion, status, usage, cancellation, and provider errors into Berry lifecycle events. Preserve the provider session id for resume. Do not represent an agent process as a text completion.
7. **Fail closed on tools.** For a shared process use the provider's empty/safe mode, remove ambient tools and credentials, register only the intersection of the role contract and Berry permissions, and keep the human release gate unchanged. Point the runtime at the berry MCP server. The task prompt names the sandbox commands, the same set on every runtime. On every subscription runtime, the berry MCP server also serves that runtime's native shell and file tool names (Kiro `execute_bash` and `fs_write`, Claude `Bash` and `Edit`, Codex `exec_command` and `apply_patch`, and the rest of each runtime's alias dictionary under `server-ts/src/agents/runtime/alias-dictionaries/`). Each one is an alias that runs the Berry tool its route names (`run_command`, `read_repository_file`, `write_file`, `edit_file`, `delete_file`, `move_file`, `browse_repository` or `fetch_url`), only when the role already has that tool, and the ledger records the Berry tool. The runtime's own tool of that name stays off or refused, and a permission prompt for a bare native name is refused. `list_run_tools` lists the aliases the session can call.
8. **Add control operations.** Implement availability, auth status, disconnect, and live model discovery through the authenticated runtime-control seam. Return only account labels and model metadata; credentials never come back.
9. **Cover transitions.** Test missing/connected/expired auth, model discovery, event ordering, cancellation/process cleanup, timeout, normalized quota/network/model errors, user isolation, and absence of fallback.
10. **Document live validation.** Automated tests mock the provider. Add real-account steps and any preview, organization-policy, geography, or plan restrictions before changing the catalog to available.
