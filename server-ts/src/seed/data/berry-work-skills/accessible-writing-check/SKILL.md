# Accessible Writing Check

## When to use

Content is going to the public, customers, students or staff.

Not for: Technical accessibility of software.

Load this skill when this exact piece of work is needed, not merely because the task belongs to the Editor.

## Gather first

- The content.
- Its format (web, document, email, slides).

## Deliverable

Produce a checklist result: heading structure, link text, alt text, reading level, plain language, tables, colour-only meaning and contrast notes, with fixes.

## Steps

1. Check headings follow a logical order.
2. Check links say where they go.
3. Check every meaningful image has alt text.
4. Estimate reading level and simplify where needed.
5. Check meaning does not rely on colour alone.

## Quality checks

- Every image is covered.
- Fixes are specific.

## Stop and hand to a person when

- The content is a legal, health or safety notice that must stay exact.

## Avoid

- Do not write alt text that repeats the caption.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

More people can read and use the content.
