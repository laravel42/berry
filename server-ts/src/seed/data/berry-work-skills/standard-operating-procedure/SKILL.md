# Standard Operating Procedure

## When to use

A task is done often, by different people, or keeps going wrong.

Not for: Software runbooks (see runbook-authoring).

Load this skill when this exact piece of work is needed, not merely because the task belongs to the Operations Coordinator.

## Gather first

- How the work is done today (notes, a walkthrough, examples).
- Who does it and who approves.

## Deliverable

Produce a procedure: purpose, when it applies, roles, numbered steps (one action each with who does it), what done looks like, common problems and fixes, and the review date.

## Steps

1. Capture the current way from a person or examples.
2. Write one action per step, starting with a verb.
3. Name who does each step.
4. Add checks at points where mistakes happen.
5. Set a review date and owner.

## Quality checks

- A newcomer could follow it unaided.
- Every step has a role.
- Done is defined.

## Stop and hand to a person when

- The procedure involves money, safety or personal data handling that has no approved policy.

## Avoid

- Do not write the ideal process nobody follows without saying so.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

Someone new can do the work correctly from the document.
