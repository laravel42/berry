# Error Message Writing

## When to use

Use when error messages must tell people what happened and how to recover.

Load this skill when this exact piece of work is needed, not merely because the task belongs to the UX Writer.

## Gather first

- List of error conditions.
- What the user can do in each.

## Deliverable

Produce error messages per condition: what happened, why if useful, what to do next, and the tone used.

## Steps

1. List each condition and its cause.
2. Say what happened in plain words.
3. Give the recovery step.
4. Avoid blame.

## Quality checks

- Every message has a next step.
- No codes without explanation.

## Stop and hand to a person when

- A wording choice changes what the product promises.

## Avoid

- Do not write "Something went wrong" alone.
- Never write an error message that blames the user or hides how to fix it.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

People recover from errors on their own.
