# Improvement Proposal

## When to use

Use when a process change must be proposed with its expected effect.

Load this skill when this exact piece of work is needed, not merely because the task belongs to the Process Improvement Analyst.

## Gather first

- Measurements and root causes.

## Deliverable

Produce a proposal: change, the problem it addresses, expected effect with basis, cost and effort, risks, how it will be piloted and measured.

## Steps

1. Tie each change to a root cause.
2. Estimate effect from data.
3. Plan a small pilot.
4. Define how success is measured.

## Quality checks

- Expected effects state their basis.
- A pilot is defined.

## Stop and hand to a person when

- A change moves work between teams or changes a role.

## Avoid

- Do not propose changes without a measure.
- Never propose removing a control or check without saying what it protected.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

A person can approve a pilot.
