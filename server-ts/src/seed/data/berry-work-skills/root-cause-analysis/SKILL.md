# Root Cause Analysis

## When to use

Use when a recurring problem in a process needs its causes found.

Load this skill when this exact piece of work is needed, not merely because the task belongs to the Process Improvement Analyst.

## Gather first

- Problem description and examples.
- Process map.

## Deliverable

Produce an analysis: problem statement, evidence, cause tree or five-whys chain, root causes with evidence, and causes ruled out.

## Steps

1. Define the problem precisely.
2. Ask why repeatedly, checking each answer with evidence.
3. Separate causes from symptoms.
4. Record what was ruled out.

## Quality checks

- Every cause has evidence.
- Blame is not a cause.

## Stop and hand to a person when

- A change moves work between teams or changes a role.

## Avoid

- Do not stop at "human error".
- Never propose removing a control or check without saying what it protected.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

The causes are known and evidenced.
