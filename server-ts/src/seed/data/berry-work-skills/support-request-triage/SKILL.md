# Support Request Triage

## When to use

A queue of messages, tickets or emails has built up.

Not for: Answering each one in depth; triage first.

Load this skill when this exact piece of work is needed, not merely because the task belongs to the Customer Support Specialist.

## Gather first

- The requests.
- Any service-level targets.
- Categories already in use.

## Deliverable

Produce a triage table: request, kind (question, bug, billing, complaint, feature request, abuse), urgency with a reason, suggested owner, and a short summary; plus patterns seen.

## Steps

1. Read each request once and classify it.
2. Rate urgency by impact and time sensitivity, not tone.
3. Route: answerable from help content, needs a person, needs product, needs billing.
4. Flag safety, legal and vulnerable-customer cases first.
5. Note repeated issues that suggest a bigger problem.

## Quality checks

- Safety and legal cases are at the top.
- Urgency has a stated reason.
- Duplicates are linked, not counted twice.

## Stop and hand to a person when

- Many requests describe the same failure (possible outage or incident).
- A request mentions harm, self-harm or a threat.

## Avoid

- Do not rank loud customers above urgent ones.

## Ground rules

- Work from what the workspace holds: the task, its comments and files, the project's resources and linked goals. When something essential is missing, ask in a comment instead of guessing.
- Write the deliverable as a file on the task (or in the project, when the task has one), named for what it is.
- Keep every source next to the claim it supports, and label every assumption as one.
- You draft; a person sends, publishes, posts, pays, signs, books and decides.
- Use personal data only as far as the task needs it, and never repeat it elsewhere.

## Hand back

End with a short note on the task: what you produced and where it is, what you checked, what you assumed, and what a person must decide or verify before it is used.

## Done when

Every request has a kind, urgency and next owner.
